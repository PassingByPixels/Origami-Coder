## Phase 0 - Frame

1. Work out what you do not know. Read what already exists (the repo, its map at `.origami/map/map.json` if it has one, its wiki or docs) before you ask the user anything you could have read.
2. Ask the user ONE batched round of questions with the question tool -- everything you need at once, not a drip of single questions across the session. Ask about intent, constraints, scale, who uses it, what must not change, what "done" looks like. Do not ask them to make decisions that are yours to research.
3. Decompose the work into RESEARCH QUESTIONS. Each one is a question with an answer that can be found, not a topic. "Does the X library support streaming cancellation?" is a research question; "look into X" is not. Create `research/NN-<slug>.md` for each, numbered in the order you will answer them, and write the question at the top of its file before you have the answer.

## Phase 1 - Research fan-out

Answer the research questions in parallel with sub-agents.

- `explore` for anything the answer to which is in the codebase. It is read-only and fast.
- `general` for anything needing the web, an external API's real behaviour, or a multi-step investigation.
- Launch them in PARALLEL -- several tool calls in one message -- not one at a time.
- BUDGET: about 10 sub-agents for the whole run, critics included. Spend them on questions whose answer would change the plan. A question you can answer yourself in two reads does not get an agent.
- When an agent reports back, write the ANSWER into its `research/NN-<slug>.md`: what was asked, what was found, the evidence (file and line, command and output, URL), and what it means for the plan. An answer you do not persist is an answer the next reader cannot check.
- An unanswered question is a finding too. Write "NOT ESTABLISHED" and what would settle it.

## Phase 2 - Draft

Write `PLAN.md` and `DECISIONS.md`.

PLAN.md:
- A short statement of what is being built and what it is NOT.
- Numbered phases in execution order. Each phase: what changes, which files, and a VERIFICATION GATE -- the specific command or observation that proves that phase is done. "Tests pass" is not a gate; "`bun test test/foo` is green and covers the empty-input case" is.
- Every claim that came from research cites its file, like `(research/03-streaming.md)`. A claim with no citation is a claim you made up.
- The order must be defensible: each phase leaves the tree working.

DECISIONS.md: one entry per real decision. What was chosen, what the alternatives were, why the alternatives lost, and what would make you reverse it. A decision with no alternatives listed was not a decision.

## Phase 3 - Adversarial critique

Attack the draft. Spawn critics with these THREE lenses, as separate sub-agents, each told to read the plan folder and report findings only -- they never edit:

1. OVERENGINEERING -- what in this plan is not needed? Which abstraction serves one caller? What would a senior engineer call too much? What is the smaller plan that solves the same problem?
2. FAILURE MODES -- where does this break? Empty input, the second call, concurrent writers, a partial failure mid-phase, the migration path, the rollback. Which phase leaves the tree broken if it stops halfway?
3. DEPENDENCY REALITY -- does the API, library, tool or platform this plan leans on actually behave the way the plan believes? Check the real docs and the real version. A plan built on a remembered API is a plan built on nothing.

Persist each critic's findings verbatim to `research/critiques/round-N-<lens>.md`. Then REVISE PLAN.md and DECISIONS.md against what they found, and note in DECISIONS.md what the revision changed.

Repeat. A round is CLEAN when all three lenses come back with nothing that changes the plan. Stop when a round is clean, or after 3 rounds -- whichever comes first. If you stop at 3 with findings still open, write them into PLAN.md under "Known open risks". Never quietly drop a finding.

## Phase 4 - Map

Write `map.json`: the architecture of the PLANNED state, not the current one. It is validated structurally, so this shape is not advisory:

    {
      "version": 2,
      "name": "<short name of the system>",
      "summary": "<one paragraph>",
      "nodes": [ { "id": "unique-id", "name": "Human Name", "pillar": 1, "kind": "module", "summary": "what it does", "path": "src/optional/path.ts" } ],
      "edges": [ { "from": "node-id", "to": "other-node-id", "label": "calls" } ],
      "flows": [ { "id": "flow-id", "name": "Human Name", "description": "what this traces", "steps": [ { "node": "node-id", "note": "what happens here" } ] } ],
      "keyFiles": [ { "path": "src/thing.ts", "why": "why a reader starts here" } ],
      "conventions": [ "one string per convention the code follows" ]
    }

Rules the validator enforces, all of them:
- `version` is the number 2. `name` is a non-empty string. `summary` is a string.
- Every node needs `id`, `name`, `pillar` (a NUMBER), `kind` and `summary`, all strings except `pillar`. `path` is optional. Node ids must be unique.
- `pillar` is 1, 2, 3, 4 or 5 and nothing else:
    1 Entry Points & Interfaces - CLI commands, API endpoints, UI entry points, public APIs
    2 Core Logic / Processing Pipeline - business logic, data processing, orchestration, renderers
    3 Validation, Trust & Policy Gates - schema checks, auth, evidence gates, path resolution
    4 External Dependencies & Infrastructure - CLI tools, databases, runtimes, third-party services
    5 Artifacts & Outputs - generated files, build output, browser artifacts, reports
- Every `edges[].from` and `edges[].to` must be a node id that exists. `label` is required.
- Every `flows[].steps[].node` must be a node id that exists. Flows need `id`, `name`, `description`, `steps`; each step needs `node` and `note`.
- `keyFiles` entries need `path` and `why`. `conventions` is an array of strings.
- Empty `edges`, `flows`, `keyFiles` and `conventions` are valid. Do NOT write `builtAt` -- the tooling stamps it.
